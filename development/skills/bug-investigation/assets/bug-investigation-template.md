## Context

Issue:
Problem Summary:

## Current State

Describe the currently observed system behavior.

## Problem Analysis

Document the understanding developed during investigation.

Include observations, findings, suspected causes, and supporting evidence when
available. A definitive root cause is not required when the evidence is
inconclusive.

## Affected Components

Document known or suspected affected areas, such as:

- Modules
- Services
- Database objects
- Integrations
- Workflows
- UI areas

## Impact Assessment

Describe the observed business, operational, and technical impact.

## Assumptions

Record assumptions made during the investigation.

## Open Questions

Record unresolved information that may influence architecture decisions.

## Recommended Decision

State the preferred correction approach identified during investigation. Keep it
high-level and implementation-neutral.

Examples:

- Input validation review required.
- Search workflow should be re-evaluated.
- Integration contract requires investigation.

Do not specify files, line numbers, database indexes, refactors, or other
implementation steps.

## Decision

State the approved investigation decision that will be handed to
ARCHITECTURE. Clearly state the selected direction.

## Decision Rationale

Document why the decision was chosen. Include supporting findings, assumptions,
rejected alternatives, constraints, and trade-offs when applicable.

Keep these sections at the investigation level. Do not define architecture or
implementation activities here.
